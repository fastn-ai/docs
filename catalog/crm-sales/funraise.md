## Setup

Your customers enter their API key for Funraise when they connect. Nothing else needs setting up.

## Connect in Fastn

Your customers connect Funraise from your widget. To connect an account yourself:

1. Go to **Build → Integrations → Connectors** and search for **Funraise**.
2. Select **Connect** on the Funraise card.

   <figure><img src="../../.gitbook/assets/connector-guides/fastn/connect-search.png" alt="The Connectors page in Fastn with ServiceNow typed in the search box and the ServiceNow card showing a Connect button"><figcaption><p>Search for the connector, then select Connect on its card. ServiceNow is shown here.</p></figcaption></figure>

3. Fill in the fields the form asks for, using the values from [Setup](#setup) above. Then select **Connect**.

   <figure><img src="../../.gitbook/assets/connector-guides/fastn/connect-credentials.png" alt="The Connect ServiceNow dialog with an optional account name and the Instance, Username and Password fields, and Cancel and Connect buttons"><figcaption><p>A connect form that asks for credentials. Each connector asks for its own fields.</p></figcaption></figure>

4. Check that the connection appears under **Operate → Connections** with the status `Active`. Your workflows can now use Funraise's actions.

For more detail, see [Connect an app](../../build/connectors/connect-an-app.md).

## Events

Start a workflow when one of these happens, with an [app event trigger](../../build/triggers/README.md).

<table><thead><tr><th width="240">Event</th><th width="260">Id</th><th>When it fires</th></tr></thead><tbody><tr><td>Donation created or edited</td><td><code>DONATION</code></td><td>Fired whenever a Funraise transaction is created or edited. This is the only event type Funraise emits - there are no supporter, subscription, campaign or task events. NO PER-TENANT ROUTING. requiredActions is deliberately EMPTY and this is not an oversight: the delivered body is {sentAt, event, data{...}} and carries no organization identifier anywhere. orgUUID exists on the REST donation list response but Funraise does not put it in the webhook body, so there is no payload field an APP-type requiredActions[].mappedTo could match a connection against. Consequence: routing is by eventKey ('event') ALONE, so EVERY active trigger on this connector receives EVERY delivery that reaches the shared Fastn URL. Do not deploy this expecting per-tenant fan-out to be filtered for you - if more than one Funraise organization is ever connected in the same Fastn org, each one's triggers will also fire on the other's donations, and the workflow must discriminate itself (for example on data.form.id, data.allocation.id or data.campaignPage.id, which are org-specific values the workflow author can pin). This is acceptable today mainly because Funraise allows exactly ONE webhook per organization. REGISTRATION IS EXPECTED TO FAIL - UNRESOLVED BLOCKER. On Save, Funraise POSTs to the target URL and the endpoint must echo the x-hook-secret REQUEST header back as a RESPONSE header and return 200, or the subscription is not created. Fastn's ingest cannot do that: the bodyless handshake support (GetChallengeConfig / pipeline/challenge-echo.ts in the event service) can READ a token from a request header, but it only ever writes the token back into the response BODY as text/plain or JSON - it never sets an arbitrary response header. This is the same class of blocker as Microsoft Graph's validationToken echo. Until Fastn's ingest grows a response-header echo, expect Funraise's Save to reject the Fastn URL and no event to ever arrive. Not reproduced against a live Funraise org - there are no Funraise credentials - but confirmed on the Fastn side by reading the ingest pipeline. SETUP (for when the above is resolved): in Funraise go to Settings &gt; Webhooks, open the Webhook Signing Secret actions menu (3 dots) and click Generate, then click Edit and paste the Fastn webhook URL as the Webhook Target URL plus a contact email for delivery failures, and Save. Funraise allows exactly ONE webhook per organization, and retries a failing delivery for about 24 hours before emailing the contact address.</td></tr></tbody></table>
