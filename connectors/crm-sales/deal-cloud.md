# DealCloud

<img src="../../.gitbook/assets/connectors/deal-cloud.png" alt="DealCloud logo" width="64">

DealCloud by Intapp - CRM and deal management for private capital, investment banking and professional services. Its data model is configured per customer: every site defines its own objects ("entry types") and fields, addressed by numeric id or apiName, so this connector is schema-driven rather than object-specific. Schema-discovery actions (entry types, fields, choice values, field types, currencies, filter operations, site users) pair with generic entry-data actions parameterised by entryTypeId: the Rows API for whole records (read, query, create, update, saved views), the Cells API for field-level create/upsert and filtering, plus delete, merge, change history for delta sync, point-in-time data, file download and template reports. Also user management, Relationship Intelligence import, site backups and the Publications event stream. Host is per tenant (https://{site}.dealcloud.com); auth is OAuth2 client credentials. DealCloud has no outbound webhooks - Publications is long-polled.

## Use it

Add DealCloud from **Build → Integrations → Connectors** and connect an account, as in [Connect a system](../../build/connectors/connect-a-system.md). In workflow code, call an action as `fastn.connector.dealCloud.<action>()`, with the action's slug from the table below. See [Workflow runtime API](../../reference/workflow-runtime.md).

## Actions

| Action | Slug | What it does |
| --- | --- | --- |
| Acknowledge Publication | `acknowledgePublication` | Commit your position in a Publication topic so the next session resumes from there instead of replaying from the beginning. Two traps worth getting right: acknowledge the CURRENT offset PLUS ONE, because the endpoint acknowledges everything up to but not including the offset you send - sending the current offset replays the last message. And an acknowledgement does not move the live session's cursor: it only takes effect when a new session starts, which happens five minutes after the last poll. Returns 204. |
| Add Choice Field Values | `addChoiceFieldValues` | Append new choice values to an existing Choice field (fieldType 2). This is the only write operation in the whole DealCloud Schema API and the only way to change a site's schema programmatically - every other schema change must be made through Object Management in the DealCloud app. Returns 400 if the target field is not a Choice field. |
| Add Existing User | `addExistingUser` | Shadow-add an existing DealCloud Universe user to this site: no email invitation is sent and no acceptance is needed, the user is simply added. Only users whose email domain matches the site's dedicated domain are eligible - anyone else must go through Invite User. Same body shape as Invite User, including temporary access via duration. |
| Create Cell Entries | `createCellEntries` | Create entries field by field using the Cells API. Each storeRequest names one entryId, one fieldId and one value; requests sharing the same negative entryId become one new record, so -1 is row one and -2 is row two. POST creates only, so every entryId must be negative and not already exist - use Upsert Cell Entries to touch existing records. Up to 10000 fields per payload, and if any single item is invalid the entire payload fails. Do not split one entry across two payloads: a negative entryId is only meaningful within its own request. |
| Create Entry Rows | `createEntryRows` | Create records of any entry type, in bulk. The body is a JSON array of up to 1000 entries, each of which MUST carry a negative EntryId (-1, -2, ...) to mark it as new; reusing the same negative id across entries in one batch links them as references to each other, which is how you create, say, a parent and child company in a single call. Field keys are the entry type's apiNames, and every choice and reference value must be the numeric id, never the display name - use List Fields by Entry Type and the Cells filter to resolve those first. The response echoes each created entry with its real, positive EntryId. |
| Create User | `createUser` | Create a brand-new user whose email is not already in the DealCloud Universe. If that email already exists anywhere in DealCloud this returns an error - use Invite User or Add Existing User instead. Two email side effects to plan for: omitting password sends a password-reset email, and creating the user active sends a verification email. To provision silently, create with isActive false; no email is sent, even when the user is activated later. twoFactorEnabled can be turned on here but cannot be turned off through the API. |
| Create User Proxy Assignment | `createUserProxy` | Authorise a proxy user to act on behalf of one or more principal users. This is what makes the AS-USER header work: a proxied API call is serviced as if the principal user made it, honouring their permissions, data access and audit trail. Both fields are required, and the call REPLACES the proxy user's existing assignments rather than adding to them - send the complete list every time. |
| Delete Entries | `deleteEntries` | Delete whole entries of an entry type, by entry id. This removes the entire record - to clear a single field instead, update it with null or an empty string. Deletion can be confirmed through Get Entry History, which is the only place deleted entries surface (isDeleted true). |
| Delete Site Backup | `deleteBackup` | Delete a site backup by name. Note two quirks: the operation is a POST, not a DELETE, and the name must be given WITHOUT the .zip extension - take the name from List Site Backups and strip the suffix. |
| Delete User | `deleteUser` | Remove a user from the DealCloud site by user id. Needs the user_management scope and a user group with user-management capability. Consider deactivating via Update User instead when audit history should stay attributable. |
