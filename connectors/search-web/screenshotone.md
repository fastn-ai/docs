# ScreenshotOne

<img src="../../.gitbook/assets/connectors/lg/screenshotone.png" alt="ScreenshotOne logo">

ScreenshotOne is a screenshot and website-rendering API that turns any URL, raw HTML or Markdown into a PNG, JPEG, WebP, GIF, MP4/WebM video or PDF. This connector covers the complete api.screenshotone.com surface: the GET and POST forms of the screenshot endpoint with every documented rendering option (viewport and device emulation, full-page and element capture, clipping, dark mode, ad/cookie-banner/tracker blocking, geolocation, proxies, cookie and header injection, custom CSS and JS, caching, S3-compatible storage upload, metadata extraction, async rendering and webhook callbacks), the animated screenshot endpoint for GIF, MP4, WebM and AVIF in both GET and POST forms, the bulk rendering endpoint, API usage and credit metrics, the supported viewport device catalogue, the service health probe and the machine-readable OpenAPI specification.

## Use it

Add ScreenshotOne from **Build → Integrations → Connectors** and connect an account, as in [Connect a system](../../build/connectors/connect-a-system.md). In workflow code, call an action as `fastn.connector.screenshotone.<action>()`, with the action's slug from the table below. See [Workflow runtime API](../../reference/workflow-runtime.md).

## Actions

<table><thead><tr><th width="240">Action</th><th width="260">Slug</th><th>What it does</th></tr></thead><tbody><tr><td>Animate Website By URL</td><td><code>animateWebsiteByUrl</code></td><td>Records a website as an animated screenshot using the GET form of the ScreenshotOne animate endpoint. This is the quick path: supply the page URL, the animation scenario ('default' stands still, 'scroll' produces a scrolling screenshot), the output container and the recording length in seconds. For scroll tuning, easing, navigation, viewport emulation, blocking, storage upload or any other option, use the Render Animated Screenshot action, which exposes the complete option set over POST. Animated renders consume more credits than a still screenshot; check Get API Usage first.</td></tr><tr><td>Bulk Render Screenshots</td><td><code>bulkRenderScreenshots</code></td><td>Builds render requests for many pages in a single call. Supply a set of shared default options plus a list of per-request option overrides; ScreenshotOne merges each request over the defaults and returns the fully-formed render URL for every one of them, as a top-level JSON array. With execute set to false nothing is rendered and no credits are spent, so this is the cheap way to generate a batch of render URLs. With execute set to true ScreenshotOne runs each render and adds a per-request execution summary carrying the status and any error; the images themselves are not returned inline. Bulk requests draw on the same per-minute concurrency bucket as single renders, so read concurrency.remaining from Get API Usage before draining a large queue. Security note: ScreenshotOne embeds your access key in plain text in every render URL this endpoint returns, so treat the output as secret and do not log or forward it.</td></tr><tr><td>Get API Usage</td><td><code>getApiUsage</code></td><td>Returns the ScreenshotOne API usage metrics for the account that owns the access key: the total number of screenshot credits in the current billing period, how many have been used, how many remain, and the current concurrency limit with the remaining concurrent slots and the reset timestamp. The standard rendering options also apply: viewport and device emulation, ad, cookie-banner, chat and tracker blocking, proxies, cookie and header injection, custom CSS and JavaScript, caching and upload to S3-compatible storage. Set response_type to 'json' to receive a URL to the recording rather than the raw file inline. Supports viewport and device emulation, full-page and element capture, clipping, dark mode and print media emulation, ad / cookie-banner / chat / tracker / social blocking, geolocation and time-zone spoofing, proxies, cookie and header injection, custom CSS and JavaScript, caching, upload to S3-compatible storage, page metadata extraction, asynchronous rendering with a webhook callback, and failure conditions. Each successful render consumes one screenshot credit.</td></tr></tbody></table>

## Events

Start a workflow when one of these happens, with an [app event trigger](../../build/triggers/README.md).

<table><thead><tr><th width="240">Event</th><th width="260">Id</th><th>When it fires</th></tr></thead><tbody><tr><td>Screenshot Rendered</td><td><code>screenshot.rendered</code></td><td>Fires when ScreenshotOne finishes a render that was submitted with a callback URL. ScreenshotOne has NO webhook registration API and no webhook management screen: a callback is requested per render, not subscribed once. To make this trigger fire, copy this trigger's webhook URL and pass it as the webhook_url option on a Render Screenshot or Render Animated Screenshot action, together with response_type set to 'json'. Set async to true so the render runs in the background and the action returns at once; the result then arrives here. To upload to your own S3-compatible bucket and receive the object location, also set store to true, supply the storage_* options, and set storage_return_location to true. By default only successful renders are delivered; set webhook_errors to true to receive failures here as well. ScreenshotOne signs the body with your secret key and sends the signature in the x-screenshotone-signature header unless you set webhook_sign to false; it also sends x-screenshotone-trace-id, x-screenshotone-reference and, when you set the external_identifier option, x-screenshotone-external-identifier, which is the field to correlate a delivery back to the render you submitted. This schema is modelled from ScreenshotOne's documented callback body plus the live response body observed from POST /take with response_type=json; it was not captured from a real delivery, because a delivery requires a publicly reachable callback URL.</td></tr></tbody></table>
